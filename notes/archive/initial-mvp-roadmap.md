# 灵策：从最小调度闭环到生产能力

本文是学习与实现计划，所有里程碑均未实现、未运行验证。

## 学习方式

每轮按以下顺序进行：确定一个可观察的结果 → 阅读相关历史源码 → 解释必要概念 → 学习者手写 → 代码审查 → 运行与验证 → 记录限制及下一轮目标。

先在本地启动程序连接 Kubernetes，完成基本闭环；之后将组件部署进集群。两种运行方式使用同一套业务实现。当前只进行静态规划。

## 迭代路线

| 阶段 | 可观察的结果 | 本轮重点 |
| --- | --- | --- |
| M0：连接集群 | 本地程序读取目标集群中的 Node 与待调度 Pod，并输出摘要 | 最小入口、客户端配置、API 访问、错误处理 |
| M1：最小调度 MVP | 提交指定 schedulerName 为 lingce 的简单 Pod，灵策选择节点并通过 Binding API 完成绑定，观察 Pod 运行与结束 | 只处理自己负责的未绑定 Pod；明确支持范围内的 CPU/内存核算、节点可用性、串行决策和失败处理 |
| M2：最小作业闭环 | 提交灵策 Job，Controller 创建所需 Pod，经灵策调度后执行，作业汇总完成或失败状态 | 最小 Job/TaskSpec API、对象归属、重复协调幂等、状态更新和删除生命周期 |
| M3：事件驱动与恢复 | 资源变化驱动协调；重复事件、重启和 API 短暂失败后能继续工作 | Informer、Lister、工作队列、重试、缓存与本地资源占用的一致性；结合上游演进调整模块边界 |
| M4：批调度 | 满足一组任务的最小调度门槛后推进分配；不足时撤销本轮试分配 | PodGroup、Gang、快照、Session、Statement、资源账本；解释调度门槛与容器同时运行的区别 |
| M5：多租户资源治理 | 多条队列和多个作业竞争时，可以解释资源分配结果 | Queue、权重、公平性、配额、抢占、回收、预留；按具体场景逐项引入策略及插件扩展点 |
| M6：大数据与训练集成 | 接入真实大数据和分布式训练作业，解释启动、资源与性能行为 | 按依赖逐项学习 Spark、PyTorch、Ray 等集成，设备资源、GPU 共享、NUMA 与网络拓扑 |
| M7：完整覆盖与生产验收 | 有依据地完成灰度接入、容量评估、故障恢复和升级回滚 | 补齐剩余 Controller、Admission、CLI、Agent、混部、网络 QoS、分片及 Agent Scheduler 等；高可用、权限、指标、性能、测试与发布 |

M0 是准备里程碑；M1 才是第一次由灵策实际做出调度决策的 MVP。第一版调度器仅面向明确约束的实验工作负载，支持范围需要写入说明并验证。

M2 结束后具备最小作业管理与调度闭环。后续每轮保持已有场景可验证；复杂阶段继续拆成小里程碑。

## 正确性与健壮性

从第一版就处理可能导致错误绑定、重复创建和错误资源核算的基本问题。不能等到生产阶段才补这些约束。

第一版可在限定场景下采用串行处理和直接读取 API；资源分配必须考虑已有占用和本轮已做出的决策，绑定失败必须处理状态恢复。

高可用、大规模优化、复杂策略和完善的运维体系随阶段增加。每轮明确支持范围、已验证行为、未解决问题以及下一阶段需要改进的地方。

## 命名与源码对应

- 产品与组件统一使用 Lingce；Go module 在实际初始化时确定。
- 通用领域名保持可对照，例如 Job、TaskSpec、PodGroup、Queue、Controller。
- 字段随真实需求增加；适用时沿用上游名称、类型与语义，差异需要说明。
- API Group、标签、注解、schedulerName 和选主锁是不同用途的标识，应逐项确定。
- 当前目标是学习和实现可追踪的行为，不宣称已兼容 Volcano API。
- 每个功能记录参考提交、源码路径、采用的设计以及暂时省略的内容；复用代码保留相关许可证和归属声明。
